Техническое задание проекта
В этом спринте вам предстоит реализовать базовые возможности интернет-магазина. Пользователи смогут просматривать список доступных товаров и добавлять их в корзину, после чего товары будут забронированы на складе.
Также вы напишете вспомогательные методы для управления витриной товаров и складом. Например, эти методы позволят администрации магазина добавлять новые товары для продажи.
После выполнения задания в вашем проекте появятся три модуля из тех, о которых мы рассказали в прошлом уроке:
shopping-store — отвечает за информацию о товарах;
shopping-cart — ответственен за корзину пользователя;
warehouse — отвечает за склад.
Несколько технических деталей
По итогам заданий, которые вы выполняли в уроках, в ветке develop у вас должна быть настроена реализация следующих паттернов:
Externalized Configuration с помощью Spring Cloud Config;
Service Discovery с помощью Eureka.
Новые микросервисы должны использовать эти же технологии.
Создайте ветку 7-spring-cloud-microservices, которая основана на ветке develop, и ведите разработку в ней. После завершения работы добавьте изменения в ветку develop и создайте пул-реквест на слияние с main. Он будет содержать все изменения, сделанные в рамках заданий тем и текущего задания. Обратите внимание, что настройки Eureka и Spring Cloud Config для модулей телеметрии ревьювер проверять не будет.
Обмениваться данными друг с другом микросервисы будут через REST с помощью Feign-клиентов. А если захотите обеспечить бо́льшую надёжность и стабильность работы приложения, вы также можете подключить в новых модулях функциональность Circuit Breaker.
Чтобы микросервисы могли работать вместе, важно, чтобы все они запускались на разных портах. Для этого удобно настроить случайный выбор порта для каждого из микросервисов — достаточно указать параметр server.port в конфигурации микросервисов равным 0. В результате порт будет генерироваться случайным образом, а взаимодействие микросервисов будет обеспечено через Eureka.Чтобы тесты работали корректно, важно, чтобы Eureka использовала порт по умолчанию — 8761. Также проверьте, что имена сервисов, под которыми они регистрируются в Eureka, соответствуют указанным в задании: shopping-store, shopping-cart и warehouse.
О работе с данными
Приложение должно следовать концепции Database per Service: каждый из микросервисов работает только со своими данными в БД. Следовательно, у каждого модуля должен быть собственный набор классов для модели данных и репозиториев.
В то же время для обмена данными между микросервисами применяются DTO-объекты. Эти объекты, наоборот, могут быть использованы несколькими микросервисами. Хорошая практика — выделять такие классы в отдельный модуль-библиотеку, которую другие модули смогут подключить как зависимость. Этот модуль можно назвать, например, interaction-api.
Приступаем к реализации сервисов
В проекте уже есть модуль commerce. В нём будет сосредоточен код, связанный с интернет-магазином, — аналогично тому, как в модуле telemetry сосредоточен код для работы с устройствами умного дома.
Для каждого из будущих микросервисов в модуле commerce будет создаваться отдельный подмодуль.
Витрина товаров — сервис shopping-store
Можно приступать к созданию сервисов! Первый из них — shopping-store, реализующий витрину товаров. Покупатели интернет-магазина будут получать из этого сервиса информацию о доступных товарах и на её основе принимать решение о покупке.
Создайте отдельный подмодуль в commerce с названием shopping-store. С этим модулем будут работать как клиенты интернет-магазина, так и его администрация.
С помощью shopping-store клиенты будут искать товары для заказа, выбирая их по нужной категории. Сейчас для пользователей Smart Home Technologies доступно три категории: устройства управления умным домом (CONTROL), датчики (SENSORS) и устройства, связанные с освещением (LIGHTING). Также клиенты смогут просматривать подробную информацию по товару — например, описание, фотографии и доступное количество.
Администрация интернет-магазина сможет использовать shopping-store, чтобы добавлять новые товары, редактировать и удалять существующие, а также управлять их доступным количеством.
Пользователей витрины вряд ли интересует точное количество товаров в магазине — скорее, степень их доступности. Для описания доступного количества используйте перечисление из нескольких значений. Значения могут быть следующими:
ENDED — товар закончился;
FEW — осталось меньше 10 единиц товара;
ENOUGH — осталось от 10 до 100 единиц;
MANY — осталось больше 100 единиц.
При добавлении и редактировании товаров, а также изменении доступного количества, администраторы будут передавать значение этого перечисления вместо точного числа.
Товар в shopping-store может быть в одном из двух состояний: ACTIVE(«активный») и DEACTIVATE(«неактивный»). Товар переходит в неактивное состояние, если администратор удаляет его. Это значит, что реального удаления товаров из базы данных никогда не происходит. Подобное поведение полезно, например, для хранения исторических данных. Так можно будет узнать, какие товары пользователь покупал в прошлом, даже если сейчас они уже выведены из ассортимента.
Полная спецификация в формате Open API для необходимых эндпоинтов shopping-store доступна здесь:
shopping-store.json
Реализуйте методы для shopping-store. Убедитесь, что все нужные сервису параметры конфигурации хранятся как внешние настройки в модуле сервера конфигураций и загружаются при запуске. Также проверьте, что сервис регистрируется в Eureka во время старта.
Корзина покупателя — сервис shopping-cart
Следующий сервис — shopping-cart, или корзина покупателя. Покупатели будут выбирать товары с витрины и добавлять их в корзину. В дальнейшем на основе этой информации будет оформлен заказ.
У пользователей должна быть возможность добавлять новые товары в корзину и изменять её содержимое — набор товаров и количество единиц каждого из них. 
При добавлении товара в корзину нужно проверить, достаточно ли его на складе. Реализацию проверки вы добавите чуть позже — после реализации сервиса склада .
Также по определённому запросу корзина может деактивироваться. Это значит, что она переходит в такое состояние, в котором в неё нельзя добавлять новые товары и использовать её для заказа, можно только просматривать уже добавленные позиции.
Со спецификацией методов для сервиса корзины можно ознакомиться здесь:
shopping-cart.json
Обратите внимание, что часть методов в спецификации ожидает на вход имя пользователя. На этом этапе вы не будете реализовывать в проекте авторизацию. Пока предположим, что имя пользователя, указанное в запросе, всегда валидно.
Склад — сервис warehouse
Последний сервис, который вы разработаете в этом спринте, — сервис склада, или warehouse. Спецификация для этого сервиса доступна в файле:
warehouse.json
У сервиса warehouse будет самая сложная логика среди рассмотренных, поэтому остановимся на нём поподробнее. У него будет два основных сценария использования.
Во-первых, с помощью warehouse администрация магазина будет управлять товарами на складе. Администраторы смогут добавлять на склад новые товары и загружать дополнительное количество уже существующих.
Учтите, что у товаров на складе может быть много полезных характеристик. Например, размеры (ширина, высота и глубина), вес и признак хрупкости. Все эти характеристики важны при оформлении, сборке и доставке товаров.
Кроме того, сервис склада будут использовать другие сервисы в процессе работы с корзиной товаров, оформления заказов и их доставки. На текущем этапе вам нужно добавить два вспомогательных метода:
Проверка доступности товаров на складе. Этот метод получает на вход корзину пользователя и должен проверить, достаточно ли на складе товаров, чтобы пользователь мог оформить заказ. Если товаров недостаточно, пользователь должен понять, каких именно из них не хватает.
Получение адреса склада. Этот метод понадобится в дальнейшем для работы сервисов доставки и оплаты, но вы реализуете его уже сейчас. Для простоты адрес будет принимать только одно из двух значений — ADDRESS_1 или ADDRESS_2. Выбор конкретного значения будет происходить случайным образом при инициализации склада. Для этого можно использовать следующий код:

private static final String[] ADDRESSES = 
        new String[] {"ADDRESS_1", "ADDRESS_2"};

private static final String CURRENT_ADDRESS = 
        ADDRESSES[Random.from(new SecureRandom()).nextInt(0, ADDRESSES.length)]; 
При этом в работе с адресами в системе должен использоваться универсальный формат — объект с полями «страна», «город», «улица», «дом», «квартира». Чтобы преобразовать этот адрес в такой формат, продублируйте строку ADDRESS_1 или ADDRESS_2 в каждое из полей.
Создаём Feign-клиенты
Пора научить новые сервисы взаимодействовать друг с другом. Для этого вы будете использовать технологию Feign-клиентов. Она позволит максимально просто и удобно выполнять REST-вызовы и обмениваться данными между сервисами.
Одно из важных преимуществ Feign-клиентов — то, что с их помощью можно гарантировать соблюдение контракта между клиентом и сервисом. Для этого код интерфейса Feign-клиента разделяется между клиентом и сервисом: клиент использует его как Feign-клиент, а сервис имплементирует как обычный Java-интерфейс. Это гарантирует, что сервис реализует все необходимые клиенту операции с правильной сигнатурой. 
В проекте вы будете использовать именно такой подход. Для этого Feign-интерфейсы сервисов необходимо вынести в часть проекта, которая будет доступна всем модулям. Подойдёт модуль interaction-api, где уже размещены классы DTO.
Разработайте интерфейсы Feign-клиентов для каждого из модулей на основе доступных в них методов. Убедитесь, что классы контроллеров реализуют эти интерфейсы. Затем вернитесь к методу добавления товара в корзину в модуле shopping-cart. Реализуйте в нём обращение к складу для проверки наличия выбранных товаров. Используйте разработанный Feign-интерфейс склада.
Задание со звёздочкой: добавляем Circuit Breaker
Основная часть задания завершена. Но мы предлагаем вам бросить себе вызов и пройти дополнительное испытание — добавить в проект поддержку Circuit Breaker.
В уроках курса вы познакомились с базовыми сценариями использования паттерна. Теперь вам нужно пойти дальше и настроить интеграцию Spring Cloud Circuit Breaker с Feign. В этом вам поможет документация.
Ваша задача — сделать так, чтобы при запросах из сервиса shopping-cart к сервису warehouse использовался Circuit Breaker. Если сервис склада недоступен, пользователь должен сразу получить осмысленный ответ.
Попробуйте подобрать наиболее подходящие параметры для настройки Circuit Breaker. Учтите, что обращения к сервису склада (в отличие от обращений к корзине пользователя), скорее всего, будут происходить не слишком часто.
На этом пока всё! В следующем спринте вы добавите в магазин оставшиеся сервисы, так что Smart Home Technologies будет полностью готов к покорению новых рынков.
