Снимки состояния умного дома
Главная задача разрабатываемой системы — реализовать работу сценариев умного дома. Вспомните схемы данных для хранения сценариев. Каждый сценарий может содержать набор условий, в основе которых — показания разных датчиков.
Вот пример такого сценария. Необходимо включать свет в прихожей, когда человек возвращается домой, а в прихожей темно. Реализовать этот сценарий можно на основе показаний двух датчиков: освещения и движения. Условия  могут быть следующими:
уровень освещения ниже 20 ЛК;
обнаружено движение.
Чтобы сценарий сработал, нужно чтобы условия одновременно выполнились. Но уровень освещения — это продолжительное событие. Естественное освещение в квартире или доме меняется в зависимости от положения солнца в течение суток. Условие «Уровень освещения ниже 20 ЛК» наступает в какой-то момент и длится в течение долгого времени. А событие «Обнаружено движение» более дискретно и длится недолго.

На схеме вы можете увидеть, что уровень освещения меняется постепенно. Умный дом может зафиксировать уровень света, необходимый для сценария, раньше, чем кто-то войдёт в прихожую. Да и вряд ли хозяин квартиры проведёт здесь в движении весь вечер и всю ночь.
Не забываем, что нам важно, чтобы выполнились сразу два условия:

Чтобы реализовать функциональность сценариев умного дома, нужно, чтобы у вас была возможность проверять текущее состояние всех датчиков, указанных в сценарии. Для этого сформируем статический срез состояния всех датчиков умного дома в каждый момент времени.

Такой срез состояния также называют снимком или снапшотом (от англ. Snapshot). Чтобы получить снапшот, нужно агрегировать события датчиков в одном объекте, который будет содержать все текущие показания.
Пользователи системы могут создать сценарии на основе показаний только своих датчиков. Эти датчики привязаны к хабу, установленному в квартире или доме. На каждый хаб нужно собрать отдельный снапшот, агрегирующий показания датчиков этого хаба.
Ваша задача — написать сервис Aggregator. Он должен читать события от устройств из топика telemetry.sensors.v1. На основе данных в каждом полученном событии должен составляться срез состояния умного дома. Другими словами, все события агрегируются в снапшоты. Каждый снапшот содержит текущие показания датчиков, зарегистрированных в конкретном хабе.
Каждый раз, когда состояние снапшота меняется, Aggregator должен записывать его в топик telemetry.snapshots.v1. Далее эти снапшоты обработает другой сервис, который будет сверять срез состояния датчиков с зарегистрированными сценариями. И, если состояние датчиков будет соответствовать условиям, этот сценарий будет активирован.

Снапшоты, как и все остальные данные, записываемые в Kafka, будем кодировать в двоичный формат Avro. Далее рассмотрим схему для хранения данных снапшотов.
Схема данных снапшотов
Как вы выяснили ранее, снимок состояния умного дома — это показания всех устройств, привязанных к конкретному хабу в определённый момент. Значит, можно составить следующий список полей снапшота:
идентификатор хаба;
метка времени, к которой относится срез состояния;
набор состояний устройств.
Разберём, что такое набор состояний. Состояние устройства — это его показания в определённый момент. Другими словами, это метка времени и набор полей, присущих датчику. Ранее вы уже определяли схемы для показаний разных датчиков:
ClimateSensorAvro,
LightSensorAvro,
MotionSensorAvro,
SwitchSensorAvro,
TemperatureSensorAvro.
Эти схемы можно использовать и для снапшота состояний. Объединив всё вместе, вы получите протокол:

@namespace("ru.yandex.practicum.kafka.telemetry.event")
protocol SensorsSnapshotProtocol {

  // импортируем схемы, которые создали ранее
    import idl "SensorEvent.avdl";

  // Схема снапшота
    record SensorsSnapshotAvro {
        string hubId;                      // идентификатор хаба
        timestamp_ms timestamp;            // метка времени снимка
        map<SensorStateAvro> sensorsState; // набор состояний, где ключ - id устройства
    }

  // схема состояния датчика
    record SensorStateAvro {
        timestamp_ms timestamp;  // время отправки показаний
        union {                  // показания конкретного датчика
            ClimateSensorAvro,
            LightSensorAvro,
            MotionSensorAvro,
            SwitchSensorAvro,
            TemperatureSensorAvro
        } data;
    }
} 
Разместите эту схему в модуле avro-schemas, в папке telemetry.
Кодирование и декодирование двоичных данных
Для отправки снапшотов в топик Kafka можно использовать тот же сериализатор, что и в сервисе Collector. Он универсален, и подходит для сериализации любых экземпляров классов, которые были сгенерированы из схем Avro. А вот для декодирования двоичных данных придётся написать десериализатор, реализующий интерфейс Deserializer.
Вспомните десериализатор, который вы рассматривали в теме о форматах данных. В нём был класс WeatherEventAvroDeserializer, реализация которого подойдёт для решения поставленной задачи.
Вместо класса WeatherEvent будем использовать SensorEventAvro. Вы можете скопировать код класса WeatherEventAvroDeserializer, заменив только класс события, которое будет декодироваться.
Но в системе, которую вы разрабатываете, есть и другие схемы Avro. Рано или поздно их тоже придётся декодировать. И тогда нужно будет копировать код десериализатора и для HubEventAvro, и для SensorsSnapshotAvro.
Чтобы не дублировать один и тот же код, воспользуйтесь инструментами абстракции и наследования. Для этого весь повторяющийся код можно вынести в базовый класс. Вместо классов конкретных событий, таких как SensorEventAvro, HubEventAvro, SensorsSnapshotAvro нужно указать параметр типа, и ограничить его сверху классом SpecificRecordBase. Так вы укажете, что базовый класс можно использовать только с экземплярами классов, сгенерированных из схем Avro.
Десериализация невозможна без схемы данных. Поэтому нужно предусмотреть конструкторы, позволяющие её указать.

public class BaseAvroDeserializer<T extends SpecificRecordBase> implements Deserializer<T> {
    // ....
    
    public BaseAvroDeserializer(Schema schema) {
        this(DecoderFactory.get(), schema);
    }
    
    public BaseAvroDeserializer(DecoderFactory decoderFactory, Schema schema) {
        // ...
    }

    // ...

    @Override
    public T deserialize(String topic, byte[] data) {
        // Код десериализации двоичных данных
    }
} 
Возьмите этот шаблон базового класса и реализуйте недостающие части. Если возникнут сложности, обратитесь к материалам из темы о форматах данных.
После реализации в базовом классе будет содержаться код, который пришлось бы постоянно повторять. Теперь, чтобы создать десериализатор конкретного события, достаточно просто расширить базовый класс:

public class SensorEventDeserializer extends BaseAvroDeserializer<SensorEventAvro> {
    public SensorEventDeserializer() {
        super(SensorEventAvro.getClassSchema());
    }
} 
Класс SensorEventDeserializer нужно указать в настройках консьюмера в качестве десериализатора для значений. Укажите его название со всеми пакетами, в которые он входит в качестве значения параметра value.deserializer (ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG).
Агрегация событий в снапшоты
Классы, которые будут сгенерированы из схем SensorStateAvro и SensorsSnapshotAvro, можно использовать не только для записи данных в топик, но и для реализации логики агрегации событий.
Для этого нужно хранить набор всех снапшотов — экземпляров класса SensorsSnapshotAvro. Когда сервис Aggregator получает новое событие от датчика, следует проверить, есть ли уже снапшот для хаба, в котором зарегистрирован датчик. Тут есть несколько вариантов дальнейших действий:
Если снапшота ещё нет. Его нужно создать, а затем добавить в набор снапшотов. Так как это будет первое событие в рамках конкретного хаба, его данные можно сразу добавить в снапшот.
Если снапшот уже был в наборе. Нужно проверить, есть ли в нём данные о конкретном датчике, событие которого вы получили. Если данных нет, нужно просто добавить данные события в снапшот хаба.
Если в снапшоте уже содержатся данные, проверьте, нужно ли их обновить. Для этого из снапшота достаньте экземпляр SensorStateAvro и сверьте его таймстемп с таймстемпом события. Если так вышло, что полученное событие произошло раньше, чем последнее обновление данных датчика, то полученное событие нужно проигнорировать.
В ситуации, когда таймстемп события больше, сверьте данные в событии и в снапшоте. Если данные отличаются, то состояние датчика в снапшоте нужно заменить данными из события. После этого нужно записать обновлённую версию снапшота в топик telemetry.snapshots.v1.
Вот псевдокод этого алгоритма:

Optional<SensorsSnapshotAvro> updateState(SensorEventAvro event) {
    Проверяем, есть ли снапшот для event.getHubId()
            Если снапшот есть, то достаём его
            Если нет, то создаём новый
    
    Проверяем, есть ли в снапшоте данные для event.getId()
            Если данные есть, то достаём их в переменную oldState
                  Проверка, если oldState.getTimestamp() произошёл позже, чем
                  event.getTimestamp() или oldState.getData() равен
                  event.getPayload(), то ничего обнавлять не нужно, выходим из метода
                  вернув Optional.empty()

    // если дошли до сюда, значит, пришли новые данные и
    // снапшот нужно обновить
    Создаём экземпляр SensorStateAvro на основе данных события
    Добавляем полученный экземпляр в снапшот
    Обновляем таймстемп снапшота таймстемпом из события
    Возвращаем снапшот - Optional.of(snapshot)
} 
Этот метод обновляет данные снапшота, только в случае необходимости. Это важное условие агрегации состояний. Поэтому он возвращает тип Optional. По нему код, вызывающий метод, поймёт, обновилось состояние снапшота или нет. Если Optional пуст, значит, снапшот не был обновлён и записывать в топик ничего не нужно. Если Optional содержит экземпляр снапшота, значит, его нужно записать в топик.
Сервис Aggregator должен записывать в Kafka снапшот только в том случае, если его данные были действительно изменены. Нет смысла записывать срез состояния, если оно не менялось. Если в топике telemetry.snapshots.v1 не появляется новых снапшотов по какому-либо хабу, нужно считать, что состояние не менялось и умному дому не на что реагировать.
Такой подход позволяет дедуплицировать повторные сообщения. Если вы уже обрабатывали событие, то оно не приведёт к генерации нового снапшота.
Управление потоком данных
Задача сервиса Aggregator —  обрабатывать поток событий от датчиков, преобразуя его в набор снапшотов. Данные читаются из Kafka и записываются обратно в него же. Это означает, что в сервисе нужно синхронизировать работу консьюмера и продюсера.
Работа консьюмера первична: если не получить данные, то не будет и результата их обработки, который нужно записать. Поэтому основа жизненного цикла сервиса Aggregator — это Poll Loop консьюмера. Именно цикл опроса станет двигателем, заставляющим Aggregator двигаться сквозь поток данных.
В прошлом уроке вы уже написали полноценное приложение-консьюмер. Возьмём этот код за основу и встроим его в Spring Boot- приложение.
Код из прошлого урока можно преобразовать в бин. Основной смысл сохранится: подписка на топики, цикл опроса, фиксация смещений. Но добавится работа с продюсером.
Нужно предусмотреть корректное завершение продюсера, а также убедиться, что перед закрытием все данные из его внутренних буфферов записаны в Kafka.

/**
 * Класс AggregationStarter, ответственный за запуск агрегации данных.
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class AggregationStarter {

    // ... объявление полей и конструктора ...

    /**
     * Метод для начала процесса агрегации данных.
     * Подписывается на топики для получения событий от датчиков, 
     * формирует снимок их состояния и записывает в кафку.
     */
    public void start() {
        try {

            // ... подготовка к обработке данных ...
            // ... например, подписка на топик ...

            // Цикл обработки событий
            while (true) {
                // ... реализация цикла опроса ...
                // ... и обработка полученных данных ...
            }

        } catch (WakeupException ignored) {
            // игнорируем - закрываем консьюмер и продюсер в блоке finally
        } catch (Exception e) {
            log.error("Ошибка во время обработки событий от датчиков", e);
        } finally {
            
            try {
            // Перед тем, как закрыть продюсер и консьюмер, нужно убедиться,
            // что все сообщения, лежащие в буффере, отправлены и
            // все оффсеты обработанных сообщений зафиксированы
                   
            // здесь нужно вызвать метод продюсера для сброса данных в буффере
            // здесь нужно вызвать метод консьюмера для фиксации смещений
                
            } finally {
                log.info("Закрываем консьюмер");
                consumer.close();
                log.info("Закрываем продюсер");
                producer.close();
            }
        }
    }
} 
Ранее все приложения, которые вы писали с использованием Spring, подразумевали, что есть сервер. Это мог быть HTTP-сервер или GRPC-сервер, как в сервисе Collector. Когда вы запускаете такое приложение, Spring Boot  запускает сервер, внутри которого есть своя вариация бесконечного цикла, реализующего жизненный цикл приложения.
В этот раз у Aggregator будет иной случай. Тут уже вам нужно позаботиться о запуске двигателя — бесконечного цикла опроса. Spring предлагает разные способы автоматического запуска методов бинов. Но сейчас воспользуемся подходом, реализованным в  приложении-потребителе из прошлого урока. В нём цикл запускался в точке входа в приложение — в методе main.
В случае Spring Boot-приложения в методе main запускается контейнер Spring. Это реализация типична для большинства таких приложений. Рассмотрим на примере сервиса Collector:

@SpringBootApplication
@ConfigurationPropertiesScan
public class Collector {
    public static void main(String[] args) {
        SpringApplication.run(Collector.class, args);
    }
} 
Этого кода достаточно. Например, в случае веб-приложения автоматически запустится HTTP-сервер, который в бесконечном цикле будет слушать сетевой порт в ожидании входящих HTTP-запросов. Или же запустится GRPC-сервер, и он тоже будет слушать порт в ожидании GRPC-запросов.
Вам же придётся самим провернуть несколько манипуляций. Метод run класса SpringApplication возвращает экземпляр контекста. Это объект класса ConfigurableApplicationContext, который содержит все бины приложения. Всё, что вам нужно сделать — достать из контекста бин AggregationStarter и вызвать его метод start.

/**
 * Главный класс сервиса Aggregator.
 */
@SpringBootApplication
@ConfigurationPropertiesScan

public class Aggregator {

    public static void main(String[] args) {
        // Запуск Spring Boot приложения при помощи вспомогательного класса SpringApplication
        // метод run возвращает назад настроенный контекст, который мы можем использовать для
        // получения настроенных бинов
        ConfigurableApplicationContext context = SpringApplication.run(Aggregator.class, args);

        // Получаем бин AggregationStarter из контекста и запускаем основную логику сервиса
        AggregationStarter aggregator = context.getBean(AggregationStarter.class);
        aggregator.start();
    }
}
